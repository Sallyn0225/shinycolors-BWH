# 闪耀色彩 28 名偶像三围数据站 PRD

- 状态：已确认，可交付实现
- 文档日期：2026-07-12
- 产品形态：React + TypeScript + Vite 静态 SPA
- UI 语言：简体中文
- 数据语言：日文主名、英文副名
- 实现状态：未开始，本仓库当前仅有数据和图片素材

## 1. 产品摘要

构建一个面向《偶像大师 闪耀色彩》粉丝的轻量数据网站，用于浏览、筛选、排序和对比当前 28 名偶像的 B/W/H 官方资料值。网站包含总榜、组合榜、双人对比三个页面。

产品核心不是判断优劣，而是准确、可追溯、易分享地呈现官方数据。所有视觉比较必须保留原始 cm 数值，不能创造综合指数或暗示身体评价。

## 2. 背景与现有资产

仓库已有：

- `shiny_colors_idol_measurements.json`：28 名成员、8 个组合、B/W/H、官方资料 URL、核验日期。
- `assets/shiny-colors/idol-icons/001.png` 至 `028.png`：28 个 54x54 RGBA 成员头像，编号对应 shinycolors.moe `idolId`，不等于当前 JSON 扁平顺序。
- `assets/shiny-colors/unit-icons/001.png` 至 `008.png`：8 个 40x40 RGBA 组合图标，编号对应 shinycolors.moe `unitId`。

当前无前端工程、依赖或部署配置。图片仍为未跟踪文件，实现前必须纳入版本控制。

## 3. 产品目标

1. 用户能在总榜按 B、W、H 任一维度查看 28 名成员的排序。
2. 用户能按组合和姓名缩小总榜结果，并明确知道当前结果数量。
3. 用户能按选定维度查看 8 个组合的平均值排名。
4. 用户能选择两个不同成员，通过三轴雷达图和原始值表完成对比。
5. 任一筛选、排序、主题或对比状态都能通过 URL 分享并在刷新后恢复。
6. 成员和组合身份色使用有证据来源的代表色，不从头像临时取色或由实现者猜测。
7. 浅色、深色、键盘、移动端和减少动效偏好均可用。

## 4. 非目标

首版不做：

- 后端、数据库、账号、收藏、评论或编辑数据。
- 身高、年龄、生日等其他资料字段。
- 成员详情页和组合详情页。
- 综合指数、胜负结论、推荐算法或统计推断。
- 多人对比、历史版本、数据上传或管理后台。
- 多语言 UI。
- 重型动效、GSAP、滚动劫持、3D 或营销落地页结构。
- 图表库、全局状态库或大型组件库。

## 5. 目标用户与核心任务

### 5.1 目标用户

- 熟悉《闪耀色彩》的中文粉丝。
- 想快速核对官方 B/W/H 资料的人。
- 想比较成员或组合相对位置的人。
- 想分享某一筛选结果或双人对比链接的人。

### 5.2 核心任务

- “按胸围从高到低看全部成员。”
- “只看アンティーカ，并搜索霧子。”
- “按腰围平均值比较 8 个组合。”
- “比较櫻木真乃与八宮めぐる，并把结果发给别人。”

## 6. 信息架构

全局导航固定为三项：

1. 总榜：`/#/overall`
2. 组合榜：`/#/units`
3. 双人对比：`/#/compare`

选择 Hash Router，保证未知静态托管平台在直接打开和刷新时无需服务器 rewrite。只有在部署平台明确支持 SPA fallback 后，才可另行决定是否改用 History Router。

全局页面框架包括：

- 顶部：产品名、三项导航、主题切换。
- 主区：页面标题、功能说明、控制区、结果摘要、数据视图。
- 页脚：数据来源、单位、最后核验日期、官方索引链接、非官方粉丝工具说明。

## 7. 功能需求

### 7.1 总榜

#### 控制项

- 测量维度：胸围 B、腰围 W、臀围 H，单选。
- 组合：全部组合或 8 个指定组合，单选。
- 姓名搜索：同时匹配日文名和英文名。
- 排序方向：降序或升序。
- 重置筛选：仅在状态偏离默认值时显示。

#### 默认状态

- 维度：胸围 B。
- 组合：全部。
- 搜索：空。
- 排序：降序。

#### 搜索规则

- 忽略前后空白。
- 英文大小写不敏感。
- 输入和目标字符串做 Unicode NFKC 规范化。
- 空字符串等同未搜索。
- 数据只有 28 条，无需 debounce。

#### 每行内容

- 可见排名。
- 成员头像。
- 日文主名、英文副名。
- 组合图标、日文组合名、英文组合名。
- 当前测量维度的原始值和单位。
- 基于全局尺度的进度条。
- 另外两项 B/W/H 紧凑数值。
- 成员官方资料链接。

#### 排名规则

- 排名在筛选后的可见结果内重新计算。
- 相同原始值采用竞赛排名，例如 1、2、2、4。
- 并列成员按 JSON 原始顺序稳定排列。

#### 进度条规则

进度条始终使用全部 28 人在当前维度的全局范围，不使用过滤后的范围。筛选时同一成员的条长不能变化。

```text
widthPercent = 12 + 88 * (value - globalMin) / (globalMax - globalMin)
```

现有全局范围：

- B：70 至 93 cm。
- W：52 至 60 cm。
- H：73 至 92 cm。

最小值显示 12%，最大值显示 100%。若未来出现 `globalMin === globalMax`，统一显示 100%。视觉百分比不作为数据对外朗读，辅助技术读取真实 cm。

#### 空状态

- 无匹配结果时保留全部筛选控件。
- 显示“没有找到符合条件的成员”。
- 提供“清除姓名搜索”和“重置全部筛选”中适用的操作。
- 不渲染空表格或占位假数据。

### 7.2 组合榜

#### 控制项

- 测量维度：B、W、H，单选。
- 排序方向：降序或升序。

#### 默认状态

- 维度：胸围 B。
- 排序：降序。

#### 每个组合内容

- 排名。
- 组合图标。
- 日文组合名、英文组合名。
- 成员数。
- 当前维度平均值，固定显示 1 位小数。
- 当前维度成员最小值至最大值。
- “查看成员”链接，跳转总榜并预设相同维度和该组合。

#### 平均值和排序规则

```text
average = sum(memberValue) / memberCount
```

- 排序使用未舍入平均值。
- 显示使用 `zh-CN` 数字格式并固定 1 位小数。
- 并列判断使用精确分数比较，可采用 `sumA * countB === sumB * countA`，避免浮点误差。
- 并列采用竞赛排名，内部按 JSON 组合顺序稳定排列。

必须覆盖的已知并列：

- W：illumination STARS 与 ALSTROEMERIA 都是 57.333... cm。
- H：illumination STARS 与 ALSTROEMERIA 都是 85.0 cm。

### 7.3 双人对比

#### 选择行为

- 成员 A 和成员 B 各一个选择器。
- 选项按组合分组，显示日文名和英文副名。
- 另一侧已选成员在当前选择器中禁用。
- 未选满两个成员时不渲染空雷达图，显示明确引导。
- 提供“交换双方”，交换身份、图形、表格和 URL。
- 不自动替用户选择默认成员。

#### 同一成员防护

- 正常 UI 禁止选择同一成员。
- URL 若传入相同 ID，保留 A、清除 B、提示选择另一名成员，并通过 replace 规范化 URL。

#### 雷达图

- 固定三轴：胸围 B、腰围 W、臀围 H。
- 每个轴单独按全部 28 人的该维度范围归一化。

```text
relative = (value - globalMin[metric]) / (globalMax[metric] - globalMin[metric])
```

- 归一化值只用于绘图，不称为分数或百分比。
- 若未来某轴 `min === max`，该轴取 0.5。
- 轴标签和图下表格显示原始 cm。
- 图下必须提供完整语义表格，雷达图不是唯一信息载体。

#### 对比表格

列为：维度、成员 A、成员 B、差值。差值定义为 A 减 B，正数显示 `+`，例如 `+4 cm`。

#### 身份信息

两侧均展示头像、双语姓名、所属组合、代表色色标和官方资料链接。

## 8. URL 状态契约

### 8.1 总榜

```text
/#/overall?metric=bust&unit=lantica&q=霧子&dir=desc&theme=system
```

- `metric`: `bust | waist | hip`
- `unit`: 合法 `unit_id`，全部组合时省略
- `q`: 搜索原文，空白时省略
- `dir`: `asc | desc`，默认 `desc` 时省略
- `theme`: `system | light | dark`，默认 `system` 时可省略

### 8.2 组合榜

```text
/#/units?metric=waist&dir=asc&theme=dark
```

### 8.3 双人对比

```text
/#/compare?a=mano_sakuragi&b=meguru_hachimiya&theme=light
```

### 8.4 更新规则

- 页面、维度、组合、排序、成员选择、交换：push 新历史记录。
- 搜索逐字输入、非法参数修正、默认参数清理：replace 当前历史记录。
- 非法值回退默认，并规范化 URL。
- 未知参数删除，确保复制链接稳定。
- URL 参数优先于本地主题偏好。
- URL 无主题时读取 `localStorage`，仍无值时跟随系统。
- 用户手动切换主题时更新 URL 和 `localStorage`。

## 9. 数据与来源需求

- `shiny_colors_idol_measurements.json` 是核心事实来源。
- B/W/H 数值和官方资料 URL 不得在组件中复制。
- 代表色也应进入同一数据契约，不能散落在 CSS 或组件条件分支中。
- 成员与组合颜色统一以用户指定的 shinycolors.moe API 为产品权威源，运行时使用本地快照，不在线请求第三方 API。
- 数据扩展时为成员加入 shinycolors.moe `source_id` 1-28，为组合加入 `source_id` 1-8。头像和组合图标文件名由该 ID 补足三位数派生，不能使用 JSON 数组下标。
- 颜色加入数据时将 `schema_version` 从 `1.0` 升为 `1.1`。
- 颜色必须携带来源、原始字段和核验日期。具体映射及字段建议见 `docs/COLOR-SOURCES.md`。
- 实现阶段修改 JSON 前后，28 名成员和 8 个组合的顺序、现有 ID、数值、来源 URL 必须保持不变。

## 10. 主题与代表色原则

- 默认跟随系统，允许手动选择浅色、深色和系统。
- 代表色用于身份色条、进度条填充、头像边框、组合图标容器和图表系列。
- 正文、按钮文字、焦点环不能直接假设代表色满足对比度。
- 近白色成员色必须通过中性外描边或底板保持可见，不能擅自改成另一种“深色版本”。
- 对比图除颜色外，使用实线/虚线、圆点/菱形和文字标签区分 A/B。
- 不随当前组合切换整页主题，避免视觉不一致。

## 11. 无障碍需求

- 语义结构包括 `header`、`nav`、`main`、`footer`，每页一个 `h1`。
- 当前导航使用 `aria-current="page"`。
- 所有控件有可见标签，不用 placeholder 代替。
- 点击目标至少 44x44 CSS px。
- 键盘可完成导航、筛选、排序、选择、交换和打开来源。
- 焦点在浅色和深色均清晰可见。
- 结果数量变化使用克制的 `aria-live="polite"`。
- 进度条的 `aria-valuenow` 是真实 cm，`aria-valuetext` 示例为“胸围 86 厘米”。
- 雷达图提供简短图像描述，下方表格提供完整替代。
- 图表和状态不只依赖颜色。
- 正文和控件达到 WCAG 2.2 AA。
- 非必要过渡在 `prefers-reduced-motion: reduce` 下关闭。

## 12. 响应式需求

- 320px 起可用，不出现页面级横向滚动。
- 小于 768px：单列控制区，排名行重排为卡片式数据行，雷达图与表格上下排列。
- 768px 至 1023px：筛选控件可换为两行，非关键列收紧。
- 1024px 及以上：内容最大宽度 1280 至 1400px，高密度数据行，雷达图和表格可并排。
- 导航桌面单行，移动端使用三项横向标签，不增加抽屉菜单。

## 13. 性能与部署要求

- 核心数据和图片全部随静态构建交付，不在运行时请求第三方核心数据。
- 图片预留固定尺寸，避免布局偏移。
- 资源路径兼容 Vite `base` 和子目录部署。
- 不需要服务端 rewrite。
- Lighthouse 建议目标：Accessibility 95 以上，Performance 90 以上。
- 目标 Core Web Vitals：LCP 小于 2.5s，INP 小于 200ms，CLS 小于 0.1。

## 15. 成功定义

首版成功不是功能数量，而是以下四点同时成立：数据准确可追溯、比较逻辑不误导、链接可复现、任何常见设备和输入方式都能完成三项核心任务。
